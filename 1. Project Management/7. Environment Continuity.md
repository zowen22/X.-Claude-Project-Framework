# Environment Continuity

Why this file exists: sessions on this framework don't run on one persistent
machine. A session might be Claude Code on the web in a container that's
reclaimed after inactivity, a mobile Cowork session with no local filesystem
at all, or a different laptop entirely from last time. **Nothing on local
disk is guaranteed to survive between sessions — only what's committed and
pushed to the git remote is durable.** This file is the operating protocol
for that reality. It is not about how to run the project locally (that's
`4. Technical Reference.md` → Environment & Setup) — it's about what a
session must assume, check, and protect against because its own environment
can vanish without warning.

-----

## The Core Rule

Treat the local working tree as disposable at every moment, not just at
session end. "I'll commit when I'm done" is not a plan — if the environment
resets mid-task, everything since the last push is gone. Commit and push
after every meaningful, working increment, not in one batch at the end.

This is the same discipline the Orchestration Cutoff Protection Protocol
uses for usage-limit cutoffs; here it's generalized to every session,
because container reclamation and cold starts are a superset of that
problem — they can happen even when no usage limit is hit.

## Session Start: Establish Ground Truth

Don't assume local state matches remote state, and don't assume the local
clone (if one even exists) reflects the last session's work. Before doing
anything else:

1. `git status` — is there a clone here at all? Uncommitted changes from a
   session that didn't finish cleanly?
2. `git branch` / `git log --oneline -5` — which branch is actually checked
   out, and does its history match what the Session Log claims was done?
3. If no local clone exists, that's normal, not an error — clone fresh from
   the remote and proceed. Don't treat a missing local history as data loss;
   the remote is the source of truth, not the local disk.
4. Confirm which branch is canonical for this session. Some environments
   hard-assign a working branch (e.g. `claude/<slug>`) rather than `main` —
   check task/session instructions before assuming `main` is what's checked
   out or what should be pushed to.

## Mid-Session Discipline

- Push after each discrete unit of work lands and verifies, not at the end.
- Confirm the push actually succeeded — don't assume silence means success.
  Proxy/auth quirks in some environments can make a push fail non-obviously;
  check the output.
- If running a multi-step task that could plausibly get cut off, checkpoint
  it in `5. Session Log.md` before starting and after finishing each step
  (see Orchestration Instructions' Cutoff Protection Protocol for the exact
  format — same protocol, applies here too).

## Recovery After an Interruption

When a session starts and the previous one may not have finished cleanly:

1. Read `5. Session Log.md` for the most recent entries — `STARTED` with no
   matching `COMPLETED`, or `[CHECKPOINT]` lines, show what was in flight.
2. `git log --oneline -10` and `git status` confirm what's actually
   committed vs. what was only ever local (and is now gone if the
   environment reset).
3. Treat any gap between what the Session Log claims and what git actually
   shows as the truth being git's version — the log is a record of intent,
   commits are the record of what landed.
4. Resume from there; don't re-do work that already landed, and don't
   assume in-progress work survived if it was never pushed.

## What This Doesn't Cover

- Local dev setup (installing dependencies, env vars, run commands) — that's
  `4. Technical Reference.md`.
- Claude's own cross-session memory system — that's `Memory vs PM Files` in
  `CLAUDE.md`. Same underlying principle (don't trust anything that isn't
  committed to the repo), different mechanism.
